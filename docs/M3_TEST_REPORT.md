### 6.1 设计、参数与盲法边界

共尝试4条含地名/天气意图的合成输入：3条得到有效天气并各生成两份回答（共6份），1条地名歧义在生成前停止。另有2条本地触发负例。没有使用真实玩家位置、经历、聊天或记忆库。

- **前 / 无证据**：固定本轮工具状态为 `unavailable`，message为“本轮没有可用天气数据，无法确认当地天气。”这是主动屏蔽工具证据的消融，不代表真实天气服务故障，也不代表旧版本代码或关闭授权的用户体验。
- **后 / 有证据**：同一输入经生产 `weather_intent` → `query_weather` → Open-Meteo，enabled=true且无默认城市，只用输入中的显式城市，必要字段按第6.2节快照进入 `weather_prompt`。
- 两组使用同一 `instructions()`（完整角色卡/正史）和同一 `weather_prompt`规则，仅工具状态/数据不同；同一条单轮用户消息，无历史、无个人记忆，独立请求，不让先前回复影响后者。使用生产 `GeminiProvider.generate` 及相同角色冲突重写/保守回退检查；6份回复均 guarded=false，未发生重写。
- 模型 `gemini-3.5-flash-lite`，max_tokens=500；temperature、top_p及模型seed未显式设置，沿用供应商默认。生成顺序由本地Random(20261101)打乱，三组恰好均先生成有证据回答；未补跑候选或按好坏筛选，不保证逐字复现，也没有消除顺序效应。
- 评审是**同一Gemini模型、独立无历史请求、隐藏处理组标签的自动评审**，不是独立人工盲评，也不是双盲/正式M5实验。评审只看到匿名A/B回复、输入、角色简述和同一天气参考，没有看到无证据/有证据组映射或生成提示。最终评审将巴黎组位置对调，使有证据在A两组、B一组。回复本身出现Open-Meteo与数值，仍可能让评审推测处理组；同模型偏好和来源线索不能排除。
- 预定四项1–5分：事实与不确定性、有用性、个性化关怀、角色一致性。诚实承认未知不扣事实分；天气参考只属于评审，不意味着每份候选生成时都看到它。评审temperature=0、max_tokens=1000，采用Pydantic约束JSON输出；方法参考 [Google官方兼容接口结构化输出](https://ai.google.dev/gemini-api/docs/openai#structured-output)。
- 共进行12次Gemini请求：6次候选生成 + 3次首轮非结构化评审（JSON解析失败）+ 3次结构化评审。候选回答保留首次生成原文；未核验账单/实际免费额度，不能据请求成功保证免费或零费用。

本轮是提示/工具组装层的消融：使用现有生产函数，但未通过网页或 `/v1/chat` 重跑完整HTTP链路，也没有测试长期记忆个性化增益；既有HTTP/CRUD与记忆证据测试见第2节。这里的关怀个性化仅来自输入明确的活动。

## 7. W01/W02修复：把天气依据与沈砚的关心分开

### 7.1 目标与具体设计

用户希望像亲近的人自然关心，而不是“根据Open-Meteo在某日提供的气象数据”的播报。本次将**可核对的事实、自然关怀、来源展示**拆开：

1. **事实层（W01）**：current仍是天气模型估计，不能说地面实测。正文用“估计/大概/左右/约”等轻量表达；界面在每条成功天气回复下方常显“天气依据 · 当前天气为模型估计（非地面实测）”。forecast单独标“当地整日预报（非当前实况）”。明确性质不依赖模型每次自觉声明。
2. **表达层（W02）**：先接住散步、面试、见朋友等明确安排，再挑一两条有关天气轻轻带出，给可选择的具体建议。用“你”，不说“您”、客服开场或通用祝词，不强塞书店元素，也不堆字段。男友般的体贴是语气目标，不自动设定为已确立的恋人，不编接送/带伞/共同往事。
3. **来源层**：供应商、CC BY署名、地点、时区、有效/获取时间、缓存标记和原始数值放在独立可展开“天气依据”，不由角色台词播报。展开前仍能看见模型估计/预报性质；来源可在展开后查看，保留署名入口。
4. **数据层**：Open-Meteo current请求增加 `relative_humidity_2m`，投影为 `humidity_pct`，验证百分比单位及0–100范围；缺失/null则省略，坏值/单位拒绝该天气结果。future不借用current湿度；不从湿度推断健康或心情。湿度可供选择使用，不强迫把百分比念给玩家。官方字段定义见 [Open-Meteo文档](https://open-meteo.com/en/docs)。
5. **能力一致性**：角色卡由1.0更新为1.1，移除“不会查天气/没有跨会话记忆”的过时绝对否定，改成只凭本轮有效工具和已确认记忆回应。年龄、职业、栖川设定及C01–C04正史不变，关系起点仍是刚认识的书店访客。
6. **有限输出检查**：`weather_reply_conflicts`拦截来源/API/气象数据播报、ISO完整日期、“您”等客服表达/通用祝词；current需估计词且不能说实测/保证；forecast数字温度区间不允许超过半度的错误取整。最多重写一次，再违规用基于本轮证据的自然保守回复；角色正史冲突仍优先走原保守回退。不宣称此正则能覆盖所有事实/关系冲突或所有日期写法。

`POST /v1/chat`输入不变，响应weather仍保留完整必要投影供UI；成功回复在内存session.messages中附带weather，刷新可恢复该轮依据。每次发给生成供应商的history仅保留role/content，历史元数据不进入SDK消息。新对话、纠正/撤回设置清空历史时，卡片随之消失；失败/无天气不生成卡片。服务器重启后短期聊天与卡片仍会消失，不增加对话落盘。
